# Graphics and backgrounds

This guide explains the tile-based background system used by the Super Nintendo and the usual PVSnesLib workflow for preparing and displaying a background. It focuses on **Mode 1**, a practical starting point for most games.

For the complete community-maintained reference, see the [PVSnesLib Wiki: Backgrounds](https://github.com/alekmaul/pvsneslib/wiki/Backgrounds).

## 1. How SNES backgrounds work

The SNES does not normally store a background as one large framebuffer. A background is assembled from three resources:

- **Tiles**: small 8×8 pixel graphics.
- **Tilemap**: a grid describing which tile appears at each position, with attributes such as palette, priority and flips.
- **Palette**: the colors used by the tiles.

The PPU reads these resources from VRAM and CGRAM to draw the screen. Reusing tiles keeps graphics data compact. Sprites are separate hardware objects and are managed through OAM.

A useful mental model is: the tile set contains the artwork, the map arranges it, and the palette supplies its colors.

## 2. Choose a graphics mode

The SNES has graphics modes 0–7. A mode determines the number of background layers available and the color depth supported by each layer.

| Mode | Background configuration | Typical use |
|---|---|---|
| 0 | Four layers, each with 4 colors | Several simple layers |
| 1 | BG1 and BG2 with 16 colors; BG3 with 4 colors | General-purpose game screens |
| 2 | Two 16-color layers, with offset-per-tile support | Distortion and scrolling effects |
| 3 | BG1 with 256 colors and BG2 with 16 colors | Detailed artwork with an overlay |
| 4 | BG1 with 256 colors and BG2 with 4 colors; offset-per-tile support | Special layered effects |
| 5 | Two layers at high horizontal resolution | High-resolution screens |
| 6 | One high-resolution 16-color layer, with offset-per-tile support | Special high-resolution effects |
| 7 | One 256-color transformable background | Rotation and scaling effects |

**Start with Mode 1 unless your project has a specific reason to use another mode.** It offers two 16-color layers plus a 4-color layer that can be useful for a HUD or text. The exact draw order also depends on tile priority and the Mode 1 BG3 priority setting.

Color index 0 in a background palette is transparent. It allows lower-priority layers or the backdrop to show through.

## 3. Prepare a background image

For a standard Mode 1 16-color background:

- Design the image using 8×8 tiles.
- Respect the 16-color limit for each tile palette.
- A 16-color background can use up to eight palettes.
- Keep in mind that tile graphics and tilemaps must fit in the SNES's limited VRAM.

PVSnesLib provides **`gfx4snes`** to convert source artwork into resources suitable for the SNES. The Wiki documents this example command for a single 16-color palette:

```makefile
pvsneslib.pic: pvsneslib.png
	$(GFXCONV) -s 8 -o 16 -u 16 -e 0 -p -m -i $<
```

The options used here are:

| Option | Meaning |
|---|---|
| `-s 8` | Use 8×8 tiles |
| `-o 16` | Use one 16-color palette |
| `-u 16` | Convert graphics in 16-color (4bpp) mode |
| `-e 0` | Start at palette entry 0 |
| `-p` | Export the palette |
| `-m` | Export map attributes |

The conversion produces resources used by the program, including tile graphics, a palette and map data. Check the options against the needs of your own artwork; the command above is an example configuration, not a universal conversion recipe.

## 4. Include converted resources in the ROM

The converted data is commonly included from an assembly file. For example:

```asm
.section ".rodata1" superfree
patterns:
.incbin "pvsneslib.pic"
patterns_end:
.ends

.section ".rodata2" superfree
map:
.incbin "pvsneslib.map"
map_end:

palette:
.incbin "pvsneslib.pal"
palette_end:
.ends
```

The start and end labels let the C code calculate each resource's size. The Wiki notes that each section must remain below 32 KB; use additional sections when the data does not fit.

Declare the labels in the C source file:

```c
extern char patterns, patterns_end;
extern char palette, palette_end;
extern char map, map_end;
```

Make sure the filenames and labels match the resources generated by your own build process.

## 5. Load tiles and palette

Use `bgInitTileSet()` to load the tile graphics into VRAM and the palette into CGRAM. A Mode 1 16-color example is:

```c
bgInitTileSet(
    0,
    &patterns,
    &palette,
    0,
    (&patterns_end - &patterns),
    (&palette_end - &palette),
    BG_16COLORS,
    0x4000
);
```

The arguments identify the background number, tile data, palette data, palette entry, data sizes, color mode and VRAM address. The example uses background 0 (BG1), `BG_16COLORS` and VRAM address `0x4000` for the tile graphics.

The address must respect the PPU's alignment requirements. Plan VRAM allocations for background tiles, tilemaps, sprite graphics and other resources together; they all share the same 64 KB VRAM space.

## 6. Load the tilemap and enable the screen

Load the map with `bgInitMapSet()`:

```c
bgInitMapSet(0, &map, (&map_end - &map), SC_32x32, 0x0000);
```

Here, `SC_32x32` selects a 32×32-tile map and `0x0000` is the map's VRAM address. PVSnesLib also defines `SC_64x32`, `SC_32x64` and `SC_64x64` for larger map layouts.

Then select Mode 1, disable layers that are not being used, and turn on the display:

```c
setMode(BG_MODE1, 0);
bgSetDisable(1);
bgSetDisable(2);
setScreenOn();
```

The background number passed to PVSnesLib functions is zero-based: `0` refers to BG1, `1` to BG2, and so on. Check the exact layer configuration in your project before enabling or disabling layers.

You normally configure the mode and layer enables during initialization, not on every frame. For updates, use the appropriate VRAM transfer functions and follow the PPU's timing constraints.

## 7. Scrolling and map dimensions

A background map is made from 32×32-tile blocks. The SNES can arrange these blocks as:

- `SC_32x32`
- `SC_64x32`
- `SC_32x64`
- `SC_64x64`

The map entry stores more than a tile number: it also contains horizontal and vertical flip flags, a palette selection and a priority bit. These attributes are why the tilemap is not simply a list of tile indices.

One detail that can surprise newcomers: a displayed background may appear to begin at vertical coordinate 1 rather than 0. This is a hardware-related behavior documented in the [PVSnesLib Community FAQ](https://github.com/alekmaul/pvsneslib/wiki/Community-FAQ). Some projects compensate by setting the vertical scroll offset to `-1`.

## 8. Plan VRAM before adding more graphics

Background tile graphics, background maps and sprite tile graphics all occupy the same 64 KB of VRAM. Reusing a VRAM address for two resources causes corruption, even if the code compiles successfully.

Before adding another layer or a large sprite set:

1. List the tile graphics and tilemaps required by each background.
2. Reserve space for sprite graphics and any console/font resources.
3. Respect the alignment required for background character data.
4. Check the resulting layout with an emulator's VRAM viewer.

The [VRAM Best Practices page](https://github.com/alekmaul/pvsneslib/wiki/VRAM-Best-Practices) gives an example memory layout and explains the address constraints. Treat its sample addresses as an example layout, not fixed addresses that every project must use.

## 10. Update a background's scroll position

Use `bgSetScroll(bgNumber, x, y)` to set the horizontal and vertical scroll values for a background. The background number is zero-based, just like the other background helpers.

The repository example `snes-examples/graphics/Backgrounds/Mode1Scroll/Mode1Scroll.c` loads a 64×64-tile map for BG2 and updates its position from the controller:

```c
u16 scrX = 0;
u16 scrY = 0;

/* During initialization: */
bgInitTileSet(1, &patterns, &palette, 0,
              (&patterns_end - &patterns), 16 * 2,
              BG_16COLORS, 0x4000);
bgInitMapSet(1, &map, (&map_end - &map),
             SC_64x64, 0x1000);

/* In the main loop: */
pad0 = padsCurrent(0);

if (pad0 & KEY_RIGHT) scrX += 2;
if (pad0 & KEY_LEFT)  scrX -= 2;
if (pad0 & KEY_DOWN)  scrY += 2;
if (pad0 & KEY_UP)    scrY -= 2;

bgSetScroll(1, scrX, scrY);
WaitForVBlank();
```

This is a shortened illustration of the example's input handling. The original sample also configures a text console and maps its VRAM separately. Its map uses `SC_64x64`, so reserve the corresponding map space in VRAM rather than copying the `0x1000` address blindly into another project.

For two independently moving layers, see `snes-examples/graphics/Backgrounds/Mode1MixedScroll/Mode1MixedScroll.c`. It calls `bgSetScroll()` with separate coordinates for BG1 and BG2. The simpler `Mode0` example also demonstrates different scroll speeds on multiple layers.

## 11. Scrolling maps larger than the resident tilemap pages

The `Mode1ContinuosScroll` example demonstrates a more advanced technique: a long horizontal level is split into map pages, and new page data is copied to VRAM as the camera advances.

The example uses `bgSetMapPtr()` to configure 64×32-tile map areas, then queues map-page updates and copies them with `dmaCopyVram()` from a custom VBlank callback registered with `nmiSet()`.

This is not just a larger value passed to `bgSetScroll()`: the program must manage which map page is currently resident in VRAM and update it at the correct time. Study the complete source at:

`snes-examples/graphics/Backgrounds/Mode1ContinuosScroll/Mode1ContinuosScroll.c`

The sample also demonstrates two layers scrolling at different speeds. Its VBlank callback checks `vblank_flag` before using the queued update data. Preserve that synchronization pattern if you adapt the example; do not copy the map-page DMA logic into the main loop without considering VBlank timing and the library's own transfers.

## 12. Transparency and color math between backgrounds

The repository example `snes-examples/graphics/Effects/Transparency/Transparency.c` demonstrates a two-layer effect in Mode 1:

- BG1 contains the land layer and uses a 16-color palette.
- BG3 contains the clouds and uses a 4-color palette.
- BG3 is enabled on the sub screen.
- Color math is configured so the sub-screen layer participates in the effect.

The core setup from the example is:

```c
bgInitTileSet(0, &LandTiles, &LandPalette, 1,
              (&LandTiles_end - &LandTiles),
              (&LandPalette_end - &LandPalette),
              BG_16COLORS, 0x0000);

bgInitTileSet(2, &CloudTiles, &CloudPalette, 0,
              (&CloudTiles_end - &CloudTiles),
              (&CloudPalette_end - &CloudPalette),
              BG_4COLORS, 0x1000);

bgInitMapSet(0, &Maps, (&Maps_end - &Maps), SC_32x32, 0x2000);
bgInitMapSet(2, &Mapsc, (&Mapsc_end - &Mapsc), SC_32x32, 0x2400);

setMode(BG_MODE1, BG3_MODE1_PRIORITY_HIGH);
bgSetDisable(1);
setScreenOn();

bgSetEnableSub(2);
setColorEffect(CM_SUBBGOBJ_ENABLE, CM_MSCR_BACK | CM_MSCR_BG1);
```

The example then scrolls BG3 while waiting for VBlank. The exact color-math flags determine which main-screen layers and backdrop take part; use the `setColorEffect()` declaration in `include/snes/video.h` and the complete example when changing the blend.

## 13. Parallax scrolling with HDMA

For a horizontal parallax effect that changes by screen region, see `snes-examples/graphics/Effects/ParallaxScrolling/ParallaxScrolling.c`.

The example fills the global `HDMATable16` with entries consisting of a line count followed by a 16-bit scroll value. It then calls `setParallaxScrolling(0)` to apply the table to BG1.

The example divides the screen into three bands:

```c
HDMATable16[0] = 72;
*(u16 *)&(HDMATable16 + 1) = 1;

HDMATable16[3] = 88;
*(u16 *)&(HDMATable16 + 4) = 2;

HDMATable16[6] = 64;
*(u16 *)&(HDMATable16 + 7) = 4;

HDMATable16[9] = 0x00; /* End of table */
```

The source header `include/snes/dma.h` documents the constraints: `setParallaxScrolling()` uses HDMA channel 3, takes a background number from 0 to 2, supports no more than 112 table values, and requires the final table entry to be `$0000`.

The example updates the three scroll values each frame and calls `setParallaxScrolling(0)`. HDMA channel 3 is therefore committed to this effect while it is active; do not assume it is available simultaneously for another effect that uses the same channel.

## 15. Notes on what these examples do not establish

The supplied examples demonstrate specific configurations, not a universal VRAM layout or a single best graphics mode for every game. In particular:

- VRAM addresses are chosen for each example's resource layout and should not be copied without checking for overlaps.
- A color-math setup is specific to its selected main-screen and sub-screen layers.
- The continuous-scroll example uses custom VBlank work and synchronization; it is substantially more complex than changing scroll coordinates.
- The parallax helper uses HDMA channel 3, so effects competing for that channel need to be coordinated.
